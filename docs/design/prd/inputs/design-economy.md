## LENS economy
成本与可靠视角：在「所有机器人共用 GLM 每 5 小时额度」「DSH 开着且电脑醒着才运行」「插件接口不稳、一处异常带崩全 App」三条硬约束下，让机器人保持主动，同时不烧光额度、不静默停摆。

## DEFINITION
主动型机器人：Agent 中心插件在 DSH 宿主里替它常开「感官」（零成本的事件监听与轮询）。机器人自己登记要盯什么（hub_watch），自己提议下次什么时候、在什么条件下再看（next_check）。信号先过规则层（二期再加小模型分诊），判定「值得想」，并且从全局额度仲裁器拿到许可，才唤醒它的大脑，也就是在它自己的会话里跑一次有边界的回合。醒来后做什么、做到哪停、要不要找主人，都由它自己决定。
与「定时任务唤醒」的区别（OpenClaw 的心跳和 cron 作业、DSH schedule 定点叫醒都属于后者）：后者只靠时间触发，到点必调模型，提示词由人写死，没有「这次不想」的选项。前者以信号触发为主，时间只做保底；机器人能塑造自己的感官和节奏，并受注意力预算约束。底层仍用计时器当闹钟（中心每 60 秒按真实时间核对一次），但闹钟由机器人自己设、可改可撤，不是人定的时间表。
判别标准（按周从唤醒账本统计）：① 大脑唤醒中，由事件、机器人自定关注、主人互动触发的占比 ≥60%；② 闸门拒掉的信号多于 0，且醒来后结果为「无变化」的比例 ≤30%；③ ≥50% 的下次唤醒时间来自机器人自己的提议；④ 每个机器人至少有 1 条自己登记的关注规则；⑤ 「需要你」都由机器人主动发起，每条只问一件事。任一项长期不达标，说明它退化成了定时任务。

## PRINCIPLES
- 感知常开、思考按需：宿主插件零成本地一直盯着，大模型只在「值得想」且拿到许可时才醒
- 三层漏斗：规则层（0 token）→ 小模型分诊（≤2k token）→ 大脑（有边界的回合）；每一层只把「有变化且有价值」的信号递给下一层
- 额度是全组共用的稀缺资源：每次思考先向仲裁器拿许可；主人自己的交互永远优先，并留保底份额
- 每次思考有三重上限：轮数、token、挂钟时间；到线先让机器人收口写回进展，再强停
- 降级优先于停摆：额度紧时先降频、合并、只留硬信号，最后才暂停；恢复时先放一个探针，再逐步放开
- 至少一次投递加幂等：每次唤醒一张唤醒单，醒来先对账；对外动作带去重键，状态未知的不自动重发
- 沉默就是故障：按每个机器人自己的节奏判断「该动没动」并主动报告，不靠主人追问
- 失败关在原地：插件绝不能带崩 DSH，出错的组件熔断自停；中心失效时机器人宁可全停，也不在没有闸门的情况下裸跑
- 状态放在会话外：唤醒单、预算、游标、进展都落盘，会话只是工作台，随时可以轮换
- 默认安静：无变化不发消息，同一阻塞只报一次，日常结果进日报；只有「需要你」和连续失败才单独打扰

## STATES
- watching｜在盯着（没在想）｜大脑没在跑，宿主按它的关注规则收集信号，不耗模型额度｜进入：机器人创建完成、回合结算完毕、退避或暂停结束｜退出：有信号通过闸门进入排队；主人暂停；熔断
- triaging｜在判断要不要处理｜小模型正在分诊一个信号包（二期）｜进入：信号包规则分在 30–69 之间｜退出：30 秒内给出结论；分诊失败或分诊额度用完时按规则分兜底
- queued｜排队中（第 N 位，预计 X 分钟）｜已获准思考，正在等全局并发名额和额度许可｜进入：闸门放行｜退出：拿到许可 → thinking；超过保质期（普通 6 小时、硬信号 24 小时）→ 过期，写进日报，不补跑
- thinking｜正在处理：<事由一句话>｜持有许可的会话回合正在运行，受轮数、token、挂钟三重上限约束｜进入：许可已发放，唤醒单已投递｜退出：turn/end；超时被取消；超额被拦
- settling｜整理结果｜宿主核对本次产出、记账、计算下次关注时间｜进入：turn/end｜退出：记账完成后转入 watching、waiting_owner、backoff 或 quota_paused
- waiting_owner｜等你回复：<一句话问题>｜已发出「需要你」；同一事由不再唤醒、不催促，不依赖主人的小步照常推进｜进入：hub_report 的状态为 needs_you｜退出：主人回复或撤销；48 小时无回复转为「搁置」并进日报
- backoff｜出错了，X 分钟后第 n 次重试｜瞬时错误后的退避等待｜进入：投递失败、限流、超时、服务端错误｜退出：到点重新排队；第 4 次仍失败 → suspended
- throttled｜省电中：只处理紧急的事｜本机器人预算用到 80%，或全局额度亮黄灯、橙灯；只接硬信号，节奏放慢一倍｜进入：预算或全局阈值触发｜退出：窗口滚动后用量回落到 70% 以下
- quota_paused｜额度用完，约 HH:MM 恢复｜不调用模型，信号照常收集｜进入：本机器人预算用尽，或识别到 GLM 额度报错（QUOTA）｜退出：到达重置时间后，探针唤醒成功
- recovering｜刚恢复，正在补看错过的事｜App 启动或电脑醒来后的对账期，不放行任何大脑唤醒｜进入：宿主启动；或 tick 发现两次检查之间时间跳了 10 分钟以上｜退出：对账完成（不超过 3 分钟），补课唤醒排进队列
- paused｜已暂停（你暂停的）｜主人手动暂停或全局急停；拦下的唤醒先存着，不丢｜进入：主人点暂停或急停｜退出：主人点恢复，存着的唤醒合并成 1 条补课
- suspended｜已停用：连续失败 N 次，需要你看一下｜熔断状态，不再自动唤醒｜进入：连续 5 次失败；preset 丢失；会话不存在｜退出：主人点「恢复」后先试运行 1 次

## WAKE SOURCES
- 文件变化：监听机器人关注的目录或文件（它自己的目录、主人授权的知识库页面、各自动线日志），30 秒防抖合并｜成本：0 token；ctx.fs.watch 只能看一层，深层目录每 5 分钟做一次快照哈希兜底｜DSH：ctx.fs.watch + ctx.interval
- DSH 会话事件：监听其它会话的 turn/end、goal/changed、approval/asked、agent/error，以及主人在普通会话里提到某个机器人关注词｜成本：0 token｜DSH：ctx.on('session/event')、goal/changed、agent/error
- 机器人自定关注（next_check / hub_watch）：机器人在回合结束时提议「何时、在什么条件下再看」，中心把时间夹在节奏上下限内存起来；到点先过规则层，条件不满足就顺延｜成本：到点前 0；到点后也先走规则层｜DSH：专属工具注册在机器人 agent.ctx 上；中心 60 秒 tick 按真实时间核对；不挂 ctx.schedule（见待决策 1）
- 主人互动：中心页的「现在想一下」按钮、主人在机器人会话里直接发消息、在飞书回复「需要你」卡片｜成本：1 次大脑唤醒；不占机器人预算，但占全局额度｜DSH：connection.fetch.register（带鉴权）；主人的直接消息本身会开回合，中心只登记、不拦
- 飞书事件：子进程订阅 @主人、群消息、文档评论、审批、日程变化，再按关注规则过滤｜成本：0 token；常驻一个子进程，内存占用待验证｜DSH：插件内 spawn lark-cli event consume（待验证）；10 分钟无输出自动重启
- 外部数据轮询：网页、RSS、行情、GitHub 等，每个源单独设间隔（默认 15 分钟，最短 5 分钟），用 ETag 或内容哈希判断有没有变化｜成本：0 token，只有网络请求｜DSH：ctx.interval + fetch；只保存哈希和摘要
- 机器人间交接：别的机器人发来的结构化交接单，经中心消息表投递，有回合上限｜成本：计入发起方的预算；消息里的「批准」一律无效｜DSH：中心自有消息表 + agent.followup（中心自有 source.kind）
- 后台任务完成：机器人醒着时启动的长命令跑完后，把它叫回来收结果｜成本：1 次续轮；maxConsecutiveWakes 设为 2｜DSH：dsh-tool-jobs completionDelivery: wakeup
- 目标临期与复查日：规则层读取机器人 goals.md 里的截止日期和复查日期，临期 24 小时内生成硬信号｜成本：0 token｜DSH：中心解析机器人目录里的文件
- 保底日结（兜底，不是主触发）：每个机器人每天一次，规则层检查当天有没有攒下的待处理信号或临期事项；没有就只在日报写一行，不调模型｜成本：多数日子 0 token｜DSH：中心 tick；时区固定写 Asia/Shanghai（定时回合拿不到浏览器时区）

## DECISION POLICY
三层漏斗，从便宜到贵依次判断。
L0 规则层（宿主代码，0 token，常开）。输入：信号摘要、来源、去重键、机器人的关注规则、静默时段、它的预算余量、全局额度灯位。处理：24 小时去重；120 秒内合并成一个信号包；打 0–100 分（来源权重 + 关注词命中 + 是否 @主人 + 是否临期）。输出：低于 30 分丢弃，只计数；30–69 分交给 L1（一期没有 L1，就攒进「下次醒来一起看」）；70 分及以上且是硬信号（主人 @、主人点按钮、交接单、24 小时内到期），直接向仲裁器申请许可。静默时段（23:00–08:00）只放行 90 分及以上的信号。
L1 分诊层（小模型，二期）。输入不超过 2k token：信号包摘要，加机器人的一页卡（目标、当前在等什么、最近 3 次结果）。输出不超过 200 token 的 JSON：verdict（ignore / log / defer / wake / ask_owner）、urgency（0–3）、一句理由、建议任务。只有 wake 且 urgency ≥2 才申请许可。次数上限：每个机器人每 5 小时 20 次，全局 120 次。分诊失败或超限时退回 L0 规则判断。
L2 大脑（完整会话回合）。拿到许可后，中心投递一张唤醒单，内容包括：事由；信号包（截断到 3k token）；上次结果；预算余量；本次上限（最多 6 轮、60k token、20 分钟）；无人值守契约（不提问，不等批准，最后一条必须是交付物，定时或信号触发都不等于主人同意）。机器人自己决定怎么做：先调 hub_checkpoint 对账；只推进一个有边界的小步；不依赖主人的事先做完；需要主人时发一条只问一件事的「需要你」；最后调 hub_report 收尾，写明五种状态之一、「世界上多了什么、谁会看到」、next_check。
自定节奏。next_check 由机器人提议（时间 + 条件 + 理由）。中心把它夹在 30 分钟到 24 小时之间，再按额度压力调整：绿灯不变，黄灯间隔翻倍，橙灯只保留硬信号。连续无变化时，间隔每次翻倍，直到上限；一有进展，就回到机器人的提议值。等主人期间不安排自定唤醒。机器人还可以用 hub_watch 增删自己的关注规则，这是它塑造自己感官的方式；这些规则由 L0 零成本执行。
新机器人的前 3 天是试运行：只开 L0，每天最多 2 次大脑唤醒，用真实消耗校准预算后再放开。

## COMPONENTS
### 信号收件箱（感知层）（它在盯什么，一期（文件、会话事件、主人操作、自定关注、日结）；二期（飞书、外部轮询））
用途：把文件、飞书、外部数据、DSH 会话事件、主人操作、机器人自定关注统一成「信号」，去重合并后落盘；整个过程不调模型。
字段：
  - signal_id：信号编号（ULID）
  - bot_id：归属机器人
  - source：来源，枚举 file | feishu | poll | session | owner | self | peer | job | daily
  - dedupe_key：来源 + 对象 + 内容哈希
  - rule_score：规则分 0–100；hard：是否硬信号
  - status：new | merged | dropped | triaging | queued | consumed | expired
  - watch_rule_id：命中的关注规则
规则：
  - 关注规则由机器人用 hub_watch 登记，中心校验后生效：每个机器人最多 20 条，默认 14 天到期，轮询间隔不低于 5 分钟，只能盯它自己的目录、主人授权的目录和白名单数据源
  - 同一 dedupe_key 在 24 小时内只算一次；同一机器人 120 秒内的信号合并成一个包
  - 每个机器人最多积压 200 条待处理信号，超出时淘汰分数最低的，并在日报计数
  - 某个来源 10 分钟内报错 5 次，就自动停掉这个来源并告警
DSH：ctx.fs.watch、ctx.interval、ctx.on('session/event' / 'goal/changed' / 'agent/error')；飞书走子进程 lark-cli event consume（待验证）；hub_watch 注册在机器人 agent.ctx 上，不注册在插件根上，以免进入普通会话；信号存 ctx.storageDomain（per-record 布局，写入前自己校验）。

### 决断漏斗（规则层 + 分诊层）（要不要想，一期规则层；二期分诊层）
用途：决定一个信号包是丢掉、记账、攒到下次，还是申请唤醒大脑，把模型调用压到最少。
字段：
  - score_drop：丢弃线，默认 30
  - score_hard：直达线，默认 70，且必须是硬信号
  - triage_cap：分诊次数上限，每个机器人每 5 小时 20 次，全局 120 次
  - verdict：ignore | log | defer | wake | ask_owner；urgency：0–3
  - quiet_hours：静默时段，默认 23:00–08:00
规则：
  - 分诊输入不超过 2k token，输出不超过 200 token 的 JSON；只有 wake 且 urgency ≥2 才申请许可
  - 机器人处于 waiting_owner 时，和它正在等的事由相同的信号一律只记账，不唤醒
  - 静默时段只放行 90 分及以上的硬信号，其余攒到 08:00 后合并处理
  - 分诊失败或额度用完时退回规则层，只有 70 分及以上的硬信号能唤醒
DSH：规则层是插件里的纯代码；分诊用 ctx.llm.stream 直接调模型（官方 auto-review 插件有先例），不开会话、不写进会话历史；能否指定 provider 和 model 待验证。

### 注意力预算与计量（思考额度，一期）
用途：给每个机器人规定每 5 小时、每天能想几次、能花多少，按真实消耗记账；超额时先降频，再暂停。
字段：
  - window_wakes_max：每 5 小时大脑唤醒上限，默认 3
  - day_wakes_max：每日上限，默认 6；day_token_cap：每日 250k token
  - wake_caps：单次上限，60k token（未缓存输入 + 输出）、20 分钟、6 轮
  - priority_class：P0 / P1 / P2，默认 P1
  - spent：本窗口和当日的次数、token、分诊次数（滚动统计）
  - trial_until：试运行截止日，前 3 天预算减半
规则：
  - 数值依据：10-16 目标钩子一天唤醒 57 次，18:34 就打光了额度；10-28 改成日目标后降到每小时 1 次。以上默认值待试跑校准
  - 计量口径：tokenUsage 增量 + compaction/summary 用量 + 分诊调用 + 搜索次数；官方统计有盲区，记账时按估算值 ×1.2
  - 用到 80% 进入 throttled；用到 100% 进入 quota_paused，直到窗口滚动或次日 00:00
  - 单次回合超过 token 或时间上限：先 steer 一句「收口：写回进展并调 hub_report」；3 分钟后仍未结束就取消回合
  - 主人手动点「现在想一下」不占机器人预算，但占全局额度；机器人多于 3 个时，每个机器人的上限从全局份额里按权重分，不能简单叠加
DSH：sessionProjections 里的 tokenUsage、contextPressure；session/event 里的 compaction/summary；agent/turn-stopping 加 sessionController.cancel（keepInbox）执行单次上限；agent/pre-step reject 做硬停；计数存 ctx.storageDomain。

### 全局额度仲裁器（总额度灯，一期（次数代理、主人保底、灯位）；二期（自动校准、避开计费高峰，后者待验证））
用途：所有机器人共用一份 GLM 5 小时额度。仲裁器负责估算余量、给主人留保底、决定谁先想。
字段：
  - window_start / reset_at：当前 5 小时窗口的起点和预计重置时间
  - bot_share_wakes：机器人每个窗口合计的大脑唤醒上限，初始 10（待校准）
  - owner_reserve：主人保底比例，默认 30%
  - light：green | yellow | orange | red
  - owner_active：主人最近 10 分钟是否在普通会话里发过消息
  - capacity_learned：从额度报错反推出来的窗口容量
规则：
  - 灯位：机器人用量低于份额的 50% 为绿灯；50–80% 为黄灯，非紧急的节奏翻倍；80–100% 为橙灯，只放行硬信号和 P0；收到 QUOTA 或份额用尽为红灯，全体机器人 quota_paused
  - 校准：第一次收到额度报错时，记下该窗口的累计用量，容量估计取该值 ×0.9，之后每次报错取较小值；连续 3 个窗口用量低于估计的 50% 且没有报错，份额上调 10%
  - 放行顺序：主人触发 > 硬信号 > P0 > 临期事项 > 排队时长（每等 30 分钟优先级 +1）> 本窗口已用比例低的优先
  - 主人活跃时，机器人并发降到 1，非紧急唤醒推迟到主人静默 10 分钟之后
DSH：监听 session/event，主人会话里 source.kind 为 user 且带 rpcId 的消息用来判断主人是否活跃；agent/request-error 读取 failure.code；agent/pre-step 拒掉没持许可的回合；状态和校准值存 ctx.storageDomain。没找到查询 GLM 余量的接口（待验证）。

### 思考调度器（并发、排队、错峰）（排队，一期）
用途：DSH 不替你排队，同时到期的机器人会一起调模型。调度器发放思考许可，控制同时在想的数量、放行节奏和启动风暴（App 重启后集中补发造成的一波调用）。
字段：
  - permit：wake_id、bot_id、granted_at、expires_at
  - max_concurrent：同时在想的大脑数，默认 2，主人活跃时为 1（参照：taskboard 默认 3、自写桥默认 2）
  - dispatch_gap：两次放行的最小间隔，默认 90 秒
  - queue_item：wake_id、bot_id、reasons[]、priority、not_before、expires_at、attempts
  - tick：60 秒一次，用 Date.now() 按真实时间核对到期
  - startup_quiet：启动静默期，默认 3 分钟
规则：
  - 同一机器人同时最多跑 1 个大脑回合；队列里同一机器人的多个唤醒合并成 1 条，事由并列
  - 队列持久化，按优先级出队；普通唤醒保质期 6 小时，硬信号 24 小时，过期的不补跑，只进日报
  - 启动或电脑醒来后，先静默 3 分钟只对账；每个机器人错过的事合并成最多 1 条补课唤醒，之后每 90 秒放行 1 个；周期性关注错过 12 小时以上的跳过本次
  - 所有自定时间加 0–10 分钟随机抖动，避免整点扎堆
  - 没持许可的回合（DSH schedule 投递、goal 自动续轮、其它插件的 followup）一律在 agent/pre-step 拦下，并把消息暂存为排队唤醒
DSH：插件自有调度，参考 dsh-taskboard 的 60 秒 tick、持久 FIFO 队列、并发闸门和放行间隔（Apache-2.0 许可）；投递用 sessionController.resolveAgent + agent.followup（中心自有 source.kind）；拦截用 agent/pre-step reject，但它会吞掉本步消息，要自己从 payload.messages 暂存（待验证）；全程走 sessionController 而不是 ctx.agents.create，以免插件重载时把机器人当轮掐断。

### 唤醒单与醒来对账（幂等）（运行记录 / 接着上次，一期）
用途：投递只保证「至少一次」，回合可能被打断。所以每次唤醒都开一张唤醒单：醒来先核对上次做到哪，副作用带去重键，重放时不会出现重复动作。
字段：
  - wake_id：唤醒单号，同时用作 prompt 的 requestId
  - phase：granted → delivered → started → ended → settled，只进不退
  - end_reason：completed | interrupted | error | cancelled | blocked | max_tokens
  - result：no_change | progress | done | blocked | needs_you | failed | unknown
  - usage：本次 token、轮数、工具调用数、耗时
  - side_effects[]：dedupe_key、类型、对象、完成时间
  - next_check：下次关注的时间、条件、理由
规则：
  - 回合第一步必须调 hub_checkpoint，拿到上次的结果、未完成的步骤和已完成的副作用清单
  - 有副作用的步骤先登记意图再执行；重放时已完成的直接跳过；状态未知的对外动作不自动重发，改成「需要你」确认
  - 最后一步必须调 hub_report；没调就记为 unknown，并算一次失败
  - 宿主重启后，凡是已投递、未结束的单都标为 interrupted，最多补发 1 次恢复唤醒，并在消息里写明「上次被打断」
  - 开始执行时已经超过 expires_at 的唤醒单，只许汇总，不许做对外动作（时间护栏）
DSH：hub_checkpoint、hub_report、hub_set_next_check 注册在机器人 agent.ctx 上；用 session/event 里 turn/end 的 reason 判断回合怎么结束；sessionController.prompt 的 requestId 去重；tools/pre-execute 拦截对外发送并查去重键；唤醒单存 ctx.storageDomain，机器人目录里的 progress 文件再存一份。

### 错误分类与退避（出错重试，一期）
用途：把失败分成几类，分别决定重试、等待、全局暂停还是找主人，不让重试放大消耗。
字段：
  - err_class：QUOTA | RATE_LIMIT | TRANSIENT | AUTH | CONTEXT | PRESET_LOST | SESSION_LOST | WRITER_HELD
  - raw：原始报错文本的前 500 字，用来补全中文额度报错的识别
  - attempts：已重试次数；next_retry_at：下次重试时间
规则：
  - QUOTA：不重试，全局亮红灯；能从报错解析出重置时间就用它，否则按窗口起点 +5 小时；到点后再过 5 分钟先放 1 个探针，成功后每 10 分钟并发 +1
  - GLM 中文额度报错：在 agent/request-error 里先按「额度、用量、上限、限额、套餐」等词和已知错误码匹配，命中就按 QUOTA 终止，免得被当成限流再重试 5 次。词表要用第一次真实报错校准（待验证）
  - TRANSIENT 和 RATE_LIMIT：DSH 自己已重试 5 次；中心再按 2 分钟、10 分钟、30 分钟、2 小时重排（±20% 抖动），第 4 次仍失败就 suspended 并告警
  - AUTH：全局暂停，发「需要你」请主人重新登录；CONTEXT：先轮换会话再重排 1 次；PRESET_LOST、SESSION_LOST：直接 suspended；WRITER_HELD：每 5 分钟重试，最多 3 次
  - 机器人所用 provider 的 retryPolicy 固定为 normal，禁止 always（always 会无限重试，连额度错误也重试）
DSH：agent/request-error（读 failure.code 并决定终止）、agent/error、turn/end；resolveAgent 抛出的 agent-preset/not-found、session/not-found、session/writer-held。遇到 GLM 超时，先排除本机 IPv6 多地址问题（dsh-net-tuning 插件已装）。

### 死人开关（停摆检测）（健康检查，一期）
用途：把任何「该动没动」都当成故障，按每个机器人自己的节奏判断，主动告诉主人，而不是等主人追问才发现。
字段：
  - expected_by：最晚应有动静的时间 = min(next_check, 最早的待处理硬信号) + 30 分钟
  - last_ok_at：最近一次成功结算的时间
  - stuck_since：回合从哪一刻起没有新事件
  - alert：原因、首次发现时间、次数、冷却到何时
规则：
  - 每次 tick 检查：到期 30 分钟后仍未唤醒，且不在暂停或额度暂停中，记为「漏醒」
  - 回合 10 分钟没有任何会话事件，或总时长超过 30 分钟：查是否挂在审批或提问上；是的话取消回合、记失败，并发「需要你」说明卡在哪
  - 3 倍 pace_max 内一次成功结算都没有，发「长期沉默」告警；感知来源（如飞书子进程）10 分钟无心跳就重启，连续 3 次失败再告警
  - 告警规则：同一原因 1 小时冷却并合并，连续 2 次才报；额度、鉴权、全体停摆立即报
  - 日报固定有一节「应醒未醒 / 卡住 / 被停用」；全部正常时也写「全部按时」
DSH：ctx.interval 60 秒；agents.get().status；session/event 里的 approval/asked 和提问事件；sessionController.cancel；如果用了 ctx.schedule，再用 catalog() 比对 scheduledAt 和 lastDelivery，找出漏投的任务。

### 宿主外看门狗与常开环境（看门狗 / 常开设置，一期只告警；二期自动重启）
用途：DSH 退出、崩溃弹窗或电脑休眠时，插件自己无能为力，需要一个 App 外的进程来发现和恢复；同时把「能不能 7×24 运行」变成看得见的指标。
字段：
  - heartbeat_file：~/.dsh/agent-hub/heartbeat.json，每 30 秒写一次（tick 序号、版本、灯位、在想的机器人）
  - stale_after：心跳陈旧阈值，默认 5 分钟
  - restart_policy：只告警 | 告警并重启（每小时最多 3 次）
  - online_coverage_7d：近 7 天计划时段的在线率
  - offline_intervals[]：离线时段及原因（休眠、退出、崩溃）
规则：
  - 用 launchd LaunchAgent 每 2 分钟检查一次：心跳陈旧且 DSH 进程不在，就重新打开 App；进程在但心跳停了，视为卡死或停在崩溃弹窗上，按 restart_policy 处理
  - 看门狗自己用 lark-cli 或飞书 webhook 发告警，不依赖 DSH 是否活着；DSH 在跑但中心心跳缺失（例如插件被「禁用第三方插件并重启」摘掉）时，告警「中心插件已停用」
  - 前提清单：插电，不合盖或改用常开的 Mac mini；接电源时防止自动睡眠或用 caffeinate；DSH 加入登录项。这些都属于改系统设置，需主人确认后由主人操作
  - 在线率低于 80% 时，日报提示「机器人有 X% 时间不在线」，并建议换常开机器
DSH：不依赖 DSH 接口，只读插件写出的心跳文件；用 open -a 拉起 App。电脑醒来后 Node 定时器会不会延迟待验证，插件按真实时间核对可以兜底。

### 离线补课与降级（离线补课，一期（文件、会话来源）；二期（飞书、轮询）；三期（云端死人开关））
用途：电脑睡着或 App 关着时什么都不会跑；恢复后有序补看错过的事，离线期间对外给出可预期的降级。
字段：
  - cursor：每个来源的已读游标（文件快照哈希、飞书消息时间戳、轮询 ETag）
  - offline_span：本次离线的起止时间
  - catchup_wakes：补课唤醒数，每个机器人最多 1 个
  - skipped：因过期跳过的事由数
规则：
  - 恢复时按游标补拉：文件对比快照，飞书按时间拉历史消息（事件订阅只能收到在线期间的事件），轮询源立刻拉一次
  - 补到的信号照常走决断漏斗，不因为欠得多就多醒
  - 离线期间到期的对外动作一律不自动执行，改成「需要你」确认；离线超过 12 小时，周期性关注只保留最近一次
  - 恢复后发一条合并消息：离线多久、补课几个、跳过几个
  - 三期：在主人自己的 VPS 上放一个云端死人开关，中心每 30 分钟 ping 一次，计划时段内 2 小时收不到就推飞书「机器人都停了」（涉及外部服务，需主人同意）
DSH：游标存 ctx.storageDomain；lark-cli 拉历史消息；tick 发现两次检查之间时间跳了 10 分钟以上，就判定刚醒来，进入 recovering。

### 适配层与插件自保（兼容性，一期）
用途：任何插件里一处没兜住的异常，都会让整个 DSH 退出并弹窗等人点；接口又会随 nightly 升级变化。中心必须保证自己永不崩溃，升级后先验证再运行。
字段：
  - host_api_probe：各宿主服务和方法的存在性探测结果
  - component_health：各组件近 10 分钟的异常数和熔断状态
  - smoke_result：升级后冒烟测试的结果和时间
  - mode：normal | maintenance（只感知，不思考）
规则：
  - 所有定时器、事件监听、HTTP 处理、子进程回调都包一层统一兜底；async 监听器必须自己 catch，否则一个未处理的 rejection 就会让整个宿主退出
  - 组件熔断：10 分钟内抛错 5 次的组件自停并告警，其余组件继续运行
  - 宿主调用只经过适配层；启动时探测 schedule、sessionController、goals、storageDomain 等服务，缺哪个就降级并报告
  - DSH 版本变化后自动进入 maintenance，跑冒烟测试（建测试会话 → prompt → 读 projections → cancel），通过后才恢复
  - 往 workspace/session-activity 贡献条目，让主人退出 App 时能看到「还有 N 个机器人在排队或思考」（待验证）
DSH：ctx.inject / ctx.get 探测服务；package.json 顶层写 engines.dsh 锁定版本；可调参数声明 .volatile()，改配置不触发插件重载；中心页接口用 connection.fetch.register（带鉴权），不用无鉴权的 webServer 路由。

### 运行模式与一键急停（一键暂停 / 省电模式，一期）
用途：给主人一个能立刻止血、又不丢东西的总开关。
字段：
  - global_mode：normal | eco（只处理硬信号、并发 1、关闭分诊）| owner_only（机器人全停，感知照常记录）| stop（感知也停）
  - bot_paused：单个机器人的暂停开关
  - stash[]：暂停期间被拦下的唤醒
规则：
  - 暂停不删除任何闹钟或关注规则，只在 pre-step 拦截并暂存；恢复时把暂存的唤醒合并成 1 条补课
  - 模式落盘，App 重启后保持不变
  - 急停同时取消正在跑的回合（保留收件箱），并暂停 goal 的自动续轮
  - 可以在中心页切换，二期也可以用飞书指令切换；每次切换写审计记录
DSH：全局 agent/pre-step reject，加 ctx.tools.guard 兜底；sessionController.cancel（keepInbox）；ctx.goals.pause；模式存 ctx.storageDomain。

### 会话轮换（控上下文成本）（换新本子，一期按 7 天固定轮换；二期按压力轮换）
用途：同一会话越跑越长，每次唤醒要发的输入 token 就越多，还会触发有损压缩。按上下文压力轮换会话，进展靠文件交接。
字段：
  - context_pressure：当前上下文压力
  - rotate_at：轮换阈值，压力 0.6 或满 7 天
  - session_history[]：新旧 sessionId
规则：
  - 在空闲时、下次唤醒之前轮换：新会话从 AGENTS.md、memory.md 和 progress 文件冷启动
  - 新会话先 rename 再首次投递，省掉自动起标题的那次额外模型调用（待验证）
  - 第一次 prompt 被接受后，才在名册里登记新 sessionId（在那之前会话还没落盘）
  - 旧会话归档，归档门禁会挡住迟到的唤醒
DSH：sessionProjections 里的 contextPressure；sessionController.create / rename / prompt；workspaceRegistry.archiveSession。


## BEHAVIORS
- 场景：平静的一天，没有值得处理的新情况
  机器人：规则层把零星的文件改动和群消息判为低分，丢弃或攒着；日结时也没发现待处理事项，全天不调模型
  主人看到：日报里一行：无变化；今天思考 0 次，收到 14 个信号，都不需要处理
- 场景：飞书文档里有人评论追问机器人负责的问题
  机器人：信号得 75 分且是硬信号 → 申请许可 → 排队 → 醒来先对账，再读评论、起草要点 → hub_report 为 needs_you，只问一件事
  主人看到：飞书一张卡片：「需要你：要不要按这 3 点回复 X 的评论？」中心页上这个机器人显示「等你回复」
- 场景：早上 9 点主人开始用 DSH，同时有 3 个机器人想思考
  机器人：仲裁器发现主人活跃，并发降到 1，非紧急的推到主人静默 10 分钟之后，其余按优先级逐个放行
  主人看到：中心页显示「排队中，第 2 位，预计 12 分钟」；主人自己的会话不受影响
- 场景：全局额度用到 80%
  机器人：亮橙灯：只放行硬信号和 P0 机器人，非紧急的自定关注推迟到窗口重置之后
  主人看到：中心页顶部横幅「额度紧张，省电中，约 15:40 恢复正常」；不单独推送
- 场景：收到 GLM 的中文额度报错
  机器人：识别为 QUOTA，不重试；所有机器人进入额度暂停，信号照常收集；到重置时间后先放 1 个探针，成功后逐步放开
  主人看到：飞书一条：「额度用完，机器人暂停到约 15:40，你自己的对话也会受影响」；恢复后不再打扰，日报记一笔
- 场景：电脑睡了 6 小时后醒来，或 App 重启
  机器人：进入 recovering：前 3 分钟只对账，把被打断的回合标为 interrupted；每个机器人错过的事合并成最多 1 个补课唤醒，每 90 秒放行 1 个；过期的对外动作改成「需要你」
  主人看到：一条合并消息：「离线 6 小时 12 分；补课 2 个机器人，跳过 5 个过期事由，1 件事需要你确认」
- 场景：某个回合卡住，例如挂在一个本不该出现的审批上
  机器人：死人开关发现回合 10 分钟没有事件、挂在审批上，于是取消回合、记失败、退避后重排；同一原因第 2 次才告警
  主人看到：第 1 次只进日报；第 2 次飞书：「X 机器人两次卡在写工作区外文件的审批上，已停下，需要你看一下」
- 场景：中心插件的某个组件反复抛异常
  机器人：这个组件熔断自停，其余照常运行，DSH 不会被带崩；如果整个中心停了，看门狗 5 分钟内发现心跳停止并告警（二期自动重启 App，每小时最多 3 次）
  主人看到：飞书：「Agent 中心的飞书订阅组件已自停（连续报错 5 次），其他机器人正常」
- 场景：机器人连续 5 次醒来都无变化
  机器人：节奏自动拉长到上限 24 小时；下次唤醒单要求它检查自己的关注规则是不是太宽
  主人看到：中心页：「最近很安静：连续 5 次无变化，最晚明天 09:30 再看一眼」
- 场景：机器人在等主人回复
  机器人：进入 waiting_owner：同一事由不再唤醒、不催促，不依赖主人的小步照常推进；48 小时没回复就转为搁置
  主人看到：只有一张待办卡；日报里写「等你 1 件（已等 26 小时）」

## GUARDRAILS
- 空转复读烧额度（10-22 那次 28 分钟被叫醒约 24 次） → 连续无变化时间隔自动翻倍；等主人期间同一事由不唤醒；同一阻塞按内容哈希只报一次；hub_report 必须带新证据才算 progress
- 一个机器人饿死全组，或挤占主人自己的会话 → 每个机器人有窗口和每日上限；全局给主人留 30% 保底；主人活跃时机器人并发降到 1；排队时已用比例低的优先
- App 启动或整点时集中补发，形成调用风暴 → 启动后静默 3 分钟；每 90 秒放行 1 个；每个机器人最多 1 个补课唤醒；所有自定时间加 0–10 分钟抖动
- 重试放大请求量 → 中心不叠加立即重试；provider 的 retryPolicy 固定为 normal；QUOTA 和 AUTH 不重试；中文额度报错在 request-error 阶段直接终止
- 静默停摆，要靠主人追问才发现 → 宿主内死人开关 + 宿主外看门狗 + 日报固定的「应醒未醒」一节；不允许把任何机器人设成「出问题也不通知」
- 插件 bug 带崩整个 DSH → 所有回调统一兜底；出错组件熔断；机器人会话不用 ctx.agents.create 持有；升级后先进维护模式跑冒烟
- 中心插件失效后，机器人在没有闸门的情况下裸跑 → 所有唤醒都由中心发起，不在 DSH schedule 里给机器人挂周期任务；万一挂了，机器人契约规定：没有唤醒单号的提醒，只回静默暗号
- 补跑产生重复副作用，或在错误的时间做事 → 唤醒单加去重键；状态未知的对外动作不自动重发；过期的唤醒只汇总，不执行
- 计量盲区导致低估真实消耗 → 把压缩摘要、分诊、搜索都计入；记账时按估算值 ×1.2；第一次额度报错后用真实点位校准
- 半夜卡在审批或提问上无限等待 → 机器人专用权限档设为 workspace-write + never；机器人 preset 去掉 ask_user_question；死人开关在 30 分钟时强制取消回合
- 夜间打扰主人 → 23:00–08:00 只记录不推送；额度、鉴权、全体停摆三类告警除外（可配置）
- 订阅条款或额度政策风险 → 上线前核实 GLM 套餐是否允许 DSH 全天后台自动调用；设机器人合计每日上限；按量 API 兜底需要主人书面批准预算

## PHASING
- 一期（MVP，最多 3 个机器人）：信号收件箱（文件、会话事件、主人操作、自定关注、日结）、规则层闸门、注意力预算与计量、全局仲裁（次数代理 + 主人保底 + 灯位）、思考调度器（并发 2、排队、启动风暴控制）、唤醒单与对账、错误分类与退避（含中文额度报错识别）、宿主内死人开关、适配层与自保、一键急停、代码生成的日报、只告警的看门狗、按 7 天固定轮换会话。上线前先试跑 3 天校准预算
- 二期（扩到 8 个机器人）：小模型分诊、飞书事件和外部轮询、完整的自定节奏（上下限 + 退避 + 额度压力调整）、离线补课、按上下文压力轮换会话、额度自动校准和避开计费高峰、看门狗自动重启、用飞书指令切换运行模式
- 三期（15 个以上机器人）：VPS 云端死人开关；评估常开 Mac mini、dsh web + launchd 常驻两种方案；按量 API 兜底和自动切换（需批准预算）；机器人间对话按「对话对」统计往返和花费，超限熔断；运行环境体检面板；计划内重启以回收常驻会话的内存（待验证）

## OPEN DECISIONS
- 机器人的「闹钟」放在哪｜选项：A 中心自有调度：60 秒 tick + 自己落盘；中心失效时机器人全停（安全，但会停） / B DSH 官方 schedule：落盘补发，会出现在「自动化任务」页；但中心失效时，机器人会在没有预算、没有并发闸门的情况下照常被叫醒 / C 混合：日结用 B，其余用 A｜建议：A。停了有看门狗和死人开关会报出来；裸跑烧额度却没人知道。自动化任务页的可见性用中心页替代
- 小模型分诊用哪个模型｜选项：A 同一 GLM 订阅里的轻量模型（不另花钱，但占同一份额度） / B DeepSeek 等按量计费的 API（便宜，不占 GLM 额度，但要另花钱） / C 不做分诊，只用规则层｜建议：一期选 C；二期先试 A，如果分诊占额度超过 10% 再换 B（花钱需要你批准月度上限）
- 机器人合计额度份额的初始值怎么定｜选项：A 先定每 5 小时合计 10 次大脑唤醒，再按额度报错校准 / B 先零代码试跑 3 天，测出真实容量再定 / C 先在 GLM 控制台查清额度口径，再按 token 定｜建议：A 和 B 同时做；如果 C 查得到，就以 C 为准
- 给你自己留多少额度保底｜选项：20% / 30% / 50%｜建议：30%，并且你活跃时机器人并发降到 1；如果你觉得自己的会话变慢了，再提到 50%
- 7×24 运行靠什么｜选项：A 现在这台电脑：插电、不合盖、防休眠 / B 一台专用的常开 Mac mini / C dsh web + launchd 常驻（未实测，而且不能和桌面版同时开）｜建议：先用 A 试跑两周，看在线率；低于 80% 再上 B；C 暂不选
- 看门狗要不要自动重启 DSH｜选项：A 只告警 / B 告警并自动结束进程、重开 App（每小时最多 3 次）｜建议：一期 A；实测确认崩溃弹窗的行为、重启不丢数据之后，二期开 B
- 夜间怎么运行｜选项：A 夜里全停 / B 只感知和记录，硬信号可以唤醒但不推送 / C 照常运行｜建议：B，并允许机器人把重而不急的活自己排到 01:00–06:00，结果进晨报（如果用的是 GLM Coding Plan，这个时段正好避开计费高峰，待验证）
- 失败了什么时候通知你｜选项：A 每次失败都报 / B 连续 2 次才报，同一原因 1 小时冷却；额度、鉴权、全体停摆立即报 / C 只进日报｜建议：B
