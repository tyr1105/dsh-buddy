# DSH 个人 Agent 中心：可行性结论

> 2026-11-04。依据：DSH 桌面版 0.2.1-rc.5 安装包里 308 个官方插件包的说明与源码，加上你已装的第三方插件和自写的控制桥。7 路细读、7 路独立核查（71 条承重结论：35 条成立，36 条方向对但要加条件，0 条被推翻），另有 1 路业界做法调研。逐条证据见 `docs/design/evidence/`；DSH 升级后，接口细节要重新核实。

## 一句话结论

能做。DSH 已经有「定时叫醒会话」「按会话设人设和目标」「插件在运行时批量开会话」这些零件，覆盖你设想的大半。缺的是把它们串起来的「Agent 中心」插件，以及无人值守时的安全和用量护栏。有两条硬约束插件解决不了：DSH 开着且电脑醒着，机器人才会醒；所有机器人共用一份模型额度。

## 一、你的设想在 DSH 里对应什么

| 你要的 | DSH 里的现成零件 | 现成程度 | 要补什么 |
|---|---|---|---|
| 很多个机器人，各有人设 | 一个机器人 = 一个长期会话 + 一个专属文件夹（AGENTS.md 自动注入）+ 共用的角色模板（preset） | 大部分现成 | 机器人名册；一键创建流程 |
| 没人找也会自己醒 | 定时服务 schedule：一次性、每隔 N 秒（至少 60 秒）、每天、每周、cron；到点在原会话里开一轮；插件可直接给任意机器人排班 | 现成 | 按事件唤醒（新文件、新飞书消息）要自写 |
| 有自己的个人目标 | /goal：一个会话一个目标，自动一轮接一轮推进 | 一半 | 开放式目标不能直接挂上去（见第二节），要「定时叫醒 + 每次一个有边界的小目标」 |
| 记得做过什么 | 会话日志永久落盘；AGENTS.md 自动注入、压缩后重新注入；自动压缩只留一份英文摘要 | 靠约定 | 进展写进机器人自己的 memory.md；会话按周轮换 |
| 能干活、能找你 | 网页抓取、命令行、MCP（接外部服务的标准插头）；找你只有应用内的侧栏标记 | 一半 | 推送飞书；每日汇总 |
| 机器人之间协作 | 官方只有父子委派、同一个「智能体团队」内互发消息 | 缺 | 自写消息通道（带回合上限）；共享看板可借鉴已装的任务看板 |
| 管得住 | 按会话设权限档；审批和工具调用都记在会话日志里 | 一半 | 无人值守权限档、预算、并发上限、一键暂停、对外发送审核 |
| 一个总览页 | 插件可在左侧栏加一个与「插件」「自动化任务」同级的页面 | 缺 | 自写 |
| 一直在跑 | 定时任务落盘，重启后每个周期任务补发最近一次错过的 | 受限 | 见第三节硬约束 |

## 二、推荐架构

**每个机器人做成独立的顶层会话，自写一个「Agent 中心」插件当大脑。**

- 机器人由三样东西组成：
  - 会话：它的「身体」，对话历史在里面；
  - 专属文件夹：它的「家」。AGENTS.md 写人设、长期目标和停止条件；memory.md 记进展；goals.md 记目标拆解和每期台账；
  - 角色模板（preset）：只做两三种，比如「调研型」「执行型」，不要一个机器人一个模板（模板多了启动慢、选择器乱，删改模板会让绑定它的机器人醒不来）。
- 中心插件负责：名册、创建、排班、护栏、汇报、总览页。
- 每次唤醒的节奏：定时叫醒 → 先读自己的文件 → 推进一个有边界的小目标（轮数上限 5–10）→ 写回进展 → 用固定格式报结果（无变化、有进展、完成、受阻、需要你）。

**为什么长期目标不直接挂在 /goal 上：**
- 它没有节奏，机器人一空闲就发下一轮；开放式目标永远「没完成」，会背靠背连跑到 256 轮；
- 除了轮数，没有 token、时间或金额预算；
- App 重启、升级或模型请求出错后，自动续跑会被收回，不会自己恢复；
- 定时叫醒的那一轮里，机器人自己没有权限开新目标或恢复目标，只能由插件代办；
- 目标文本只在目标轮里出现，平时的回合里机器人看不到，所以长期目标要写进 AGENTS.md。

你自己的经历印证了这一点：10-16 量化线的目标钩子一天叫醒 57 次，18:34 额度耗尽；10-28 你把目标改成「当天做完并汇报即算达成」，唤醒从每小时 8 次降到 1 次。

**不选官方实验功能「智能体团队」做骨架：**
- 队友共用总管的人设、模型和工作目录；
- 队友不能自己定时醒；
- 桌面版最多 8 个，名字永久占位、不能删；
- 总管不在内存时，全队叫不醒；
- 每个队友跑完一轮，都会把总管叫醒一轮，额度大约翻倍。

它适合在某个机器人内部临时拉一个小组干活。

## 三、两条硬约束

1. **DSH 开着、电脑醒着，机器人才会醒。** 关窗口没事，只是隐藏，后台照跑；退出 App、合盖或休眠就全停。没有开机自启，没有防休眠，崩溃后弹窗等人点。想 24 小时跑，要一台常开的电脑（比如 Mac mini）。改用命令行版 DSH 常驻理论上可行，但没实测，而且不能和桌面版同时开。
2. **所有机器人共用一份模型额度。** DSH 不会替你排队，同一时刻醒来的机器人会一起调用模型；App 启动时还会把停机期间错过的唤醒一起补发，形成一波集中调用。你 10-21 十来个任务就把 5 小时额度打光，起步只适合 2–3 个机器人、每天唤醒一两次。GLM 订阅是否允许在 DSH 里全天后台自动调用，需要核实。

## 四、必须补上的护栏

| 风险 | DSH 现状 | 补法 |
|---|---|---|
| 半夜卡死 | 审批默认无限期等人点；「向用户提问」默认也无限等 | 机器人专用权限档「工作区内可写、越界自动拒绝」（改配置即可）；机器人模板里去掉提问工具 |
| 额度烧光 | 没有预算，没有同时运行上限 | 每个机器人的预算、同时最多 N 个在跑、唤醒错峰、超额自动暂停；醒来先做便宜检查，没新情况不调用模型 |
| 数据外泄 | 沙箱只拦写文件，不拦联网和读文件；所有机器人共用一份凭据 | 「读外部内容」「能对外发送」「能读私密数据」三样最多给两样；对外发送先给你过目 |
| 静默停摆 | 唤醒失败只记一条警告，不会自动重试；重启后目标不会自己续跑 | 中心插件巡检漏投并告警；启动后重新武装目标；每天一份状态汇总 |
| 通知轰炸 | 没有任何推送 | 每天一份汇总推飞书；只有「需要你」时单独提醒，一条只问一件事 |
| 一个错误全停 | 任何插件在定时器或事件回调里一处没兜住的异常，都会让整个 DSH 退出并弹窗等人点；选「禁用第三方插件并重启」会把中心插件一起摘掉 | 中心插件所有回调兜底；外部看门狗 |
| 升级就坏 | 预发布版，插件接口没有稳定承诺；你的桥和看板都因升级坏过 | 宿主调用集中在一层适配层；每次升级后跑冒烟测试 |

## 五、建议的推进顺序

0. **零代码试跑（几天）**：用现成功能建 2–3 个机器人，每个一个文件夹，放 AGENTS.md（人设、目标、停止条件、读写记忆的规矩），再设每天定时唤醒。看三件事：醒得准不准、每天烧多少额度、产出有没有用。会消耗 DSH 额度，开跑前先定方案。
1. **MVP 插件**：名册与创建流程、排班、无人值守权限档、预算与并发上限、一键暂停、每日汇总推飞书、左侧栏总览页。
2. **再扩展**：机器人互发消息（带回合上限，消息里的「批准」一律无效）、按事件唤醒、完成评审（用另一个模型或确定规则验收，不让干活的机器人自己说了算）、更多机器人。

已装的第三方任务看板（dsh-taskboard 0.8.7，Apache-2.0 许可）已经实现了「宿主侧定时、全局并发上限 3、排队、复用会话」，可以借鉴它的执行和调度代码。不建议直接在它上面改：它的数据模型是任务卡不是机器人，上游还在快速迭代。

## 六、业界做法里最值得抄的五条

1. **醒来先做便宜检查**：先用规则或脚本判断有没有新情况，没有就不调用模型；醒了发现没事，回一个约定的静默暗号，不发消息。
2. **无人值守契约**：定时运行时没人在场，不能提问、不能等批准；最后一条必须是交付物；结果只报五种状态之一（无变化、有进展、完成、受阻、需要你）。定时触发不等于你同意了任何动作。
3. **目标写成可验证的终态，加停止条件**：停止条件至少包括「已在等你回复」「你说停」「没有不需要你拍板的步骤」「夜间时段」「最多 N 轮」。完成与否由另一个模型、确定规则或你来判。
4. **人只在三种时刻出现**：通知、提问、审核，统一进一个「待我处理」收件箱；日常产出汇总成每天一份。
5. **写死流程清单，比加一个「主管机器人」更有效**：同一个模型当主管，盲点和下属一样；多个机器人互相附和，会把一个幻觉扩散到全组。

出处和更多坑见 `docs/design/evidence/08-prior-art.md`。

## 七、还没核实、需要实测的点

- 电脑休眠醒来后，定时任务会不会推迟触发（取决于 macOS 上 Node 定时器是否计入休眠时间）。
- GLM 额度用完时的报错能否被识别（中文报错可能被当成限流，先重试 5 次）。
- GLM 订阅条款是否允许在 DSH 里全天后台自动调用。
- 机器人会话被唤醒后会一直常驻内存（没找到空闲回收），几十个机器人时的内存开销。
- 你的 profile 补丁和 `~/.dsh/cordis.patch.yml` 里是否关了热重载（按约定没读这两个配置文件）。
- 用 GLM 的机器人做网页搜索，是否必须另配 DeepSeek 的 API key（代码显示需要）。
- 运行时注册角色模板（`ctx.agentPresets.register`）与开机时会话恢复、定时补发之间的先后顺序。

## 八、顺带发现

- 「活动会话已达上限 2」是你自写控制桥的设置（`bridge.js` 的 `DEFAULT_MAX_ACTIVE_SESSIONS`，`settings.json` 可调 1–4），不是 DSH 的限制；DSH 本身没有同时活跃会话数的上限。
- drive-dsh 技能 `references/gotchas.md` 第 12 条说「联网会弹批准请求」，与代码不符：macOS 沙箱只拦写文件，联网不触发审批。当时见到的批准，多半是 npm 往工作区外写缓存被拦。
- 已装的任务看板允许 agent 用 `taskboard_create` / `taskboard_update` 把卡片权限设成完全访问，代码里没有用户确认环节。
- 控制桥把版本要求写在 `dsh.engines.dsh` 下，宿主只读顶层的 `engines.dsh`，等于没声明。
- 用 `session.selectModel` 给某个会话换模型，会顺手把全局默认模型也改掉；控制桥每派一个指定模型的任务，全局默认就被改一次。

## 九、关键接口速查（给后续开发用）

| 用途 | 接口 | 注意 |
|---|---|---|
| 建机器人会话 | `ctx.sessionController.create({cwd, agentPreset})` | 不收模型参数；第一次 prompt 被接受后才落盘，名册在那之后再登记 |
| 指定模型且不改全局默认 | `ctx.agents.create({agentOptions: {provider, model}})`，或在 `agent/request` 里改路由 | `selectModel` 会改全局默认 |
| 设权限档 | `ctx.permissionPresets.set(session, name)` | 新会话默认是「工作区可写 + 需要时询问」，批量创建时要显式夹紧 |
| 发消息叫醒 | `sessionController.prompt(...)`；或 `resolveAgent` 后 `agent.followup({content, source})` | `prompt` 的来源固定记为「用户」，要标明发送者就用后一种 |
| 排班 | `ctx.schedule.create(sessionId, {title, prompt, 六选一的时间规则})` | 浏览器端没有 create，只能宿主插件调；周期任务的消息格式是 `[SCHEDULE REMINDER BATCH]` |
| 开有边界的目标 | `ctx.goals.create(agent, {objective, maxGoalRounds})`、`ctx.goals.resume` | 不检查人类授权；轮数没有上限，要自己校验 |
| 运行时注册角色模板 | `ctx.agentPresets.register(definition)` | 只在内存，每次启动重新注册，且要赶在会话恢复之前 |
| 存名册 | `ctx.storageDomain.open({name, version, layout: 'per-record', invalidRecords: 'backup-and-skip', tables})` | 写入时不校验，写前自己校验 |
| 拦截每一步（暂停、预算） | `agent/pre-step` 返回 reject | 会吞掉本步消息，暂停期间的唤醒要自己暂存 |
| 拦截工具调用 | `tools/pre-execute`；`ctx.tools.restrict`（按机器人屏蔽工具） | `restrict` 只能在该机器人的 `agent.ctx` 上调 |
| 自动审批应答 | `approval/request` | 必须用 prepend 注册，否则会被界面转发器截走 |
| 总览页 | 客户端 slot `sidebar.panellist` + `main` | 数据接口用 `ctx.connection.fetch.register`（带鉴权），别用无鉴权的 webServer 路由 |
| 机器人专属工具和提示词 | 注册在该机器人的 `agent.ctx` 上 | 注册在插件根上会进入你所有的普通会话 |

另外：用 `ctx.agents.create/resume` 开出的会话归中心插件所有，插件一重载就会被全部取消；常驻机器人应走 `sessionController.create` / `resolveAgent`。
