# M04 维护完成记录

日期：2026-11-05。实现方：Codex，`packages/core`。任务依据：`docs/tasks/M04-createbot-with-watches.md`；核对 `docs/build-spec.md` 与 M02、M03 进度，规格和任务卡保持只读。

## 结果与根因

已修复新建机器人携带起步关注项时的落表依赖。原链路为 `createBot → makeWatch → assertWatchPathAccess → watchGateContext`：为了全部预检后才落表，`createBot` 此时只有本地 Bot，而访问检查按 id 查询 `bots`，因此 file/log 关注必然报“关注项所属机器人不存在”。

访问检查现在支持直接使用已校验的 Bot 构造 GateContext；创建预检沿途传 Bot，无需先落表。HTTP/RSS 创建和读取共用同一访问检查，运行时原有按 id 查询最新授权的路径保留。未提前写表，原有“全部预检通过后落表、创建家目录失败则撤回”的顺序不变。

同类检查发现 `validateCommand` 也按 homeDir 回查机器人以取得工作数据授权，已增加直接接收 Bot 的路径，创建、主人编辑、批准提议和运行时轮询均传已取得的 Bot。旧家目录字符串参数保持兼容，仍查询当前授权，找不到机器人时工作数据默认拒绝。家内脚本存在性、命令限制、敏感路径和工作数据边界没有放宽。

检查了志向、初始目标、周期期限、关注过滤和期望预检：初始目标通过本地 aspirations 数组关联，`makeGoal` 与 `goalPeriodEnd` 不查询未落表机器人，无需修改。

## 新增测试名与证据

`m04-createbot-watches.test.ts`（17 项）：

- `同次创建六类关注与初始目标全部落表，file/log 立即注册真实监听`：一次传入 file、log、http、rss、script、session 各一条及两个初始目标。核对 probation、trial queued、默认间隔、来源、志向关联、家目录视图；家内脚本在 MemoryFs 中真实存在，stat 预检时 bots 数为 0；file/log 的实际 FsIO.watch 调用及后续事件批次均被断言。
- `$kind 起步关注拒绝 $target，所有关联表与家目录保持原状`（10 项）：file/log 分别覆盖 `~/.ssh`、`~/.dsh/.credentials.yaml`、注入 ownerHome 对应的两种绝对敏感路径、工作数据路径。字面量 `~` 按原格式要求拒绝；绝对敏感路径明确断言“敏感凭据路径”，不能用格式错误冒充访问检查。
- `脚本起步关注拒绝 $target，预检失败不留下机器人`（5 项）：敏感 SSH、DSH 凭据参数、工作数据、真实存在的家外脚本、缺失家内脚本。
- `起步关注预检成功后初始目标关联无效，也不留下半个机器人`：合法关注先通过，随后无效 aspirationIndex 被拒绝。

所有拒绝用例都先建立已有队友、目标及真实监听，再提交“合法起步关注 + 非法关注”或非法目标；比较 bots、aspirations、watches、goals、queue 全表、文件快照、家目录清单和监听器，确认新身份不存在、拟用家目录未创建、旧队友原状保留，网络与命令执行均为零。
