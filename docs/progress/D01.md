## 路由路径的最终选择与源码依据

**选择：多段路径 `/api/agent-hub/<名字>`**（overview/bot/thread/inbox/activity/settings/recent-sessions + command）。

依据（DSH 源码只读核对）：`dsh-client-connection/lib/index.js` 的 `endpointFromPath(channel, pathname)`（926–931 行）把 `/api/` 之后的部分按 `/` 切段、逐段校验 `ENDPOINT_SEGMENT_PATTERN`，**不限制段数**；`assertFetchRoute`（973–976 行）只要求 `endpointFromPath('/api', route.path) !== undefined` 且 methods 非空不重复。`/api/agent-hub/overview` 的每段都合法，故多段路径可用。GET 全部显式 `requestBody:'buffered'`（`requestBodyMode` 原样返回 route.requestBody，只有 `'buffered'` 构造不带 body 的 Request，否则 GET 走流式分支带 body 会 400；verified-T5 Q3-1）。

1. **Settings 类型**：D01 在 `views.ts` 里按 core `SettingsSchema` 顶层字段做了局部声明（c02/c03 为不透明对象），未 import core（任务卡明确本卡不 import core）。D02 换成从 core 导入。已记 docs/questions.md。
2. **观潮与总管的 appraisals 少于 8 条**（2–4 条）：任务卡要求「为什么醒/没醒 8 条」，按「数据集中至少有一份完整 8 条」理解，给了巡检员完整 8 条（右栏展示逻辑通用，取最近 8）。已记 docs/questions.md。
3. **「打开工作会话」**按第 16 节第 5 条做了 `sessionLinkState` 的简化判断（sessions 可用性 + id 存在），不可用时右栏显示一句指引；完整五态判断留给 D02（真实 sessionId 出现后才有意义）。
4. **routes/events 的回调兜底**：fetch 处理函数在 `routes.ts` 内逐条 try/catch（而非再包一层 safe()），SSE handler 的异步路径由 hub.subscribe 内部 try/catch 兜住；语义与第 16 节第 2 条一致。
5. **fixtures 的 `color` 字段**直接放 `var(--dsw-alias-*)` token 字符串（数据里不出现裸颜色值，亮暗自动跟随）。D02 接真引擎后 color 的取值格式以 core 为准，界面用 `background: color` 渲染，token 与合法 CSS 颜色都兼容。
